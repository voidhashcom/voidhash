Observer mode lets your existing billing SDK keep control of purchases while Voidhash observes
store transactions and builds customer and entitlement state. It is the supported way to migrate an
app that already ships in-app purchases.

## The one invariant

Both SDKs may stay initialized in the same build. What must never be true is two SDKs *completing*
the same store transaction.

Exactly one integration may finish (StoreKit) or acknowledge (Google Play) a transaction. The other
one may read it, report it, and render UI from it. When Voidhash runs with `readOnly: true`, it
never finishes or acknowledges anything, so your existing SDK stays the sole owner.

Everything else on this page follows from keeping that invariant true at every moment, including
during the release where ownership changes.

## Enable observer mode

```ts title="src/lib/voidhash.ts"
import { createVoidhashClient } from "@voidhash/react-native";

export const voidhash = createVoidhashClient("vh_pk_...", {
  readOnly: true,
});
```

| Behavior                                   | `readOnly: true` | `readOnly: false` (default) |
| ------------------------------------------ | ---------------- | --------------------------- |
| Starts purchases                           | No               | Yes                         |
| Observes store transactions                | Yes              | Yes                         |
| Syncs transactions to Voidhash             | Yes              | Yes                         |
| Finishes / acknowledges store transactions | No               | Yes, after a successful sync |
| Reads products, persons, entitlements      | Yes              | Yes                         |

Voidhash also sends `x-observer-mode: true` on SDK requests while the mode is active, so the server
records that this client is observing rather than owning purchases.

### APIs blocked in observer mode

`client.purchase()` and `client.setPersonAttributesSync()` are blocked because both perform writes
owned by the normal Voidhash flow. Hosted paywall purchase actions call `client.purchase()`
internally and fail the same way — the paywall receives an error envelope and the hook's `onError`
fires.

Reading products, persons, entitlements, feature flags, and paywall assignments remains available,
as do `restorePurchases()`, queued analytics, and `setPersonAttributes()`.

## Switch ownership at runtime

`readOnly` is not fixed at construction. Flip it on the live client:

```ts
voidhash.client.setReadOnly(false); // Voidhash now owns purchases
voidhash.client.setReadOnly(true); // back to observing

if (voidhash.client.isReadOnly) {
  // render the existing SDK's purchase UI
}
```

The switch takes effect at the next decision point of each consumer: purchase gating, the
transaction observer's finish/acknowledge decision, and the `x-observer-mode` header on later
requests.

<Callout type="info" title="In-flight purchases keep the mode they started with">
  A purchase that has already begun completes under the mode that was active when it started, so a
  `setReadOnly(true)` landing mid-purchase can never strand that transaction unfinished with the
  store. Transactions already being processed when the call lands may also complete under the
  previous mode.
</Callout>

Switching at runtime avoids recreating the client, which would drop the native store connection,
the caches, and the analytics queue.

## Roll out behind a feature flag

Use one flag to decide both halves of ownership at once — which SDK's UI starts a purchase, and
which SDK finishes the resulting transaction. Reading them from a single value is what keeps the
invariant true:

```tsx title="app/paywall-entry.tsx"
const voidhashOwnsPurchases = useMyFeatureFlag("voidhash_purchases");

useEffect(() => {
  // One source of truth: the same flag that picks the UI picks the owner.
  voidhash.client.setReadOnly(!voidhashOwnsPurchases);
}, [voidhashOwnsPurchases]);

return voidhashOwnsPurchases ? <VoidhashUpgradeScreen /> : <LegacyUpgradeScreen />;
```

Apply the mode before presenting purchase UI, not after a customer taps buy. Roll the flag out to a
small percentage first, compare both platforms in the sandbox, then widen it.

To ship the SDK completely inert — no store connection, no network, no listeners — construct it
disabled instead:

```ts
export const voidhash = createVoidhashClient("vh_pk_...", {
  enabled: false,
});
```

`enabled` is fixed at construction. Mount `<voidhash.Provider>` unconditionally either way: a
disabled client still renders the provider and every hook, so hook order never changes between
builds. Enabling the SDK later means creating a new client, which is cheap because a disabled one
never built its runtime.

## Fall back when Voidhash cannot present

`show()` never rejects. Branch on its status to decide whether to fall back to the existing SDK's
paywall or an app-owned screen:

```tsx
const paywall = voidhash.usePaywallByLocation("settings-upsell", {
  onError: (error, { action }) => {
    // A purchase or restore failed *inside* an already-visible paywall.
    reportError(action, error);
  },
  onPreloadError: (error) => {
    // Background preload failed. The SDK retries; this is for reporting only.
    reportError("preload", error);
  },
});

const result = await paywall.show();

switch (result.status) {
  case "shown":
    break;
  case "not_assigned":
  case "native_unavailable":
  case "disabled":
  case "not_initialized":
    showLegacyPaywall();
    break;
  case "failed":
  case "initialization_failed":
    reportError("show", result.error);
    showLegacyPaywall();
    break;
}
```

Keep two categories apart:

- **Fallback-safe** — `not_assigned`, `not_initialized`, `native_unavailable`, `disabled`, `failed`,
  `initialization_failed`. Nothing was presented and no money moved, so showing the other paywall is
  always correct.
- **Purchase and restore failures** — delivered to `onError` with `action: "purchase" | "restore"`.
  The paywall is already on screen and a store flow may have started. Do not respond by opening a
  second paywall; surface the error and let the customer retry.

## Migration sequence

<Steps>

<Step>
### Ship Voidhash in observer mode

Add the SDK with `readOnly: true` and leave the existing integration untouched. Nothing about the
purchase flow changes in this release.
</Step>

<Step>
### Verify in the sandbox

On both iOS and Android, run a new purchase, a renewal, a cancellation, an expiry, a refund, and a
restore. Confirm each one appears on the person in Studio and produces the perk grants you expect.
</Step>

<Step>
### Compare against your current source of truth

For a sample of real customers, compare Voidhash entitlement grants with the access your existing
system grants. Investigate every mismatch before continuing — this step is what makes the switch
safe.
</Step>

<Step>
### Move purchase UI and ownership together

Put both behind one flag, as above. When the flag is on, Voidhash presents the paywall *and*
`setReadOnly(false)` makes it the owner. When it is off, both revert. Never split them across two
releases.
</Step>

<Step>
### Remove the previous SDK

Once the flag is at 100% and store transactions reconcile cleanly, delete the old integration and
drop `readOnly` from the client options.
</Step>

</Steps>

Retest new purchases, renewals, cancellations, and restores on both platforms after each step. A
transaction left unacknowledged on Google Play is refunded automatically after three days, so
ownership gaps show up as revenue loss rather than as errors.
